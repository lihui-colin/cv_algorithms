# 持续运行 20ms 优化：实施与验收

## 第六轮：候选跟踪调度实验与诊断（2026-09-17，最新）

按预先约定的门槛完成了动态分块实验，**未通过，已撤回动态分配及其构建开关**。
默认仍是原静态分配；不增加绑核、忙等或剪枝，不改变搜索及 very_high 精定位。
本轮保留：可关闭的内部线程诊断、串行/并行候选等价测试、P99/冷启动统计和验收脚本。

### 实验和门槛

实验只将候选跟踪改为原子索引每次领取 4 个候选；少于 4×线程数时仍静态分配。
各线程独立缓存，结果写回原索引。静态与动态实验版各通过 12 项 CTest，包含空批次、
小批次、非整块批次和单/多线程；样例 CSV 逐字节一致，评估位姿均为 137143。

同源码 Release 构建、诊断关闭、4 线程，每轮预热 20 帧、测试 500 帧，静态/动态交替：

| 轮次 | 静态中位 / ms | 动态中位 / ms | 静态 P95 / ms | 动态 P95 / ms |
|---|---:|---:|---:|---:|
| 1 | 17.829 | 19.248 | 21.729 | 26.135 |
| 2 | 18.510 | 18.735 | 25.666 | 24.481 |
| 3 | 17.818 | 18.145 | 22.479 | 24.089 |

第一组中位数劣化超过 2%；没有一组 P95 改善达到 5%；合并 P95 为静态 24.105ms、
动态 25.059ms。因此不满足“三组中位均不劣化超过 2%、至少两组及合并 P95 改善 5%”的门槛。
不能凭第二组 P95 改善就保留动态调度，也不能把其他阶段的波动归因于本项改动。

### 诊断结论及使用方式

另用诊断构建采集 200 帧、1200 个跟踪批次，不将这些耗时用于上述验收：

- 同批次线程开始时间差：中位 0.00476ms，P95 0.00694ms。
- 最忙线程 CPU 时间 / 批次线程均值：中位 1.092，P95 1.292。
- 最多评分次数 / 均值：中位 1.047，P95 1.124。
- 线程完成时间差：中位 0.094ms，P95 0.576ms。

存在负载差异，但该采样未显示明显的线程启动延迟；动态领任务并未产生整帧收益。
墙钟减 CPU 时间还包括测量误差和其他等待，不能直接等同于系统调度等待。
这些数据不足以将全局慢帧归因于某一种系统因素。

```bash
cmake -S shape_match_v1 -B /tmp/shape-tracking-diag -DCMAKE_BUILD_TYPE=Release -DSHAPE_MATCH_TRACKING_DIAGNOSTICS=ON
cmake --build /tmp/shape-tracking-diag -j 4
cd shape_match_v1
/tmp/shape-tracking-diag/performance_bench 200 /tmp/tracking-diagnostic.json
```

默认选项 OFF；开启后额外生成 `.tracking.csv`，每行记录帧/批次/层/线程、相对提交时刻的
dispatch/start/end/completed、线程 CPU 时间、候选数、评分次数。
Linux 之外 CPU 时间为 -1；worker 不写文件，benchmark 在全部匹配完成后输出。
提交线程的内部收集器最多保留 512 批，benchmark 每帧取走并清空，预热记录丢弃；
诊断构建的其他调用方必须及时取走记录，超限记录不保留。公共匹配 API 未变。

`scripts/evaluate_tracking_schedule.py DIRECTORY` 按固定门槛评估实验目录内三组 JSON/CSV，
同时汇总跟踪阶段中位/P95/P99；不根据测量结果调整门槛。
原实验可执行文件与源码快照保留在本次临时目录 `/tmp/tracking-plan-kxZ2JK`，不作为产品路径。

## 第五轮：高斯滤波的数据布局与累加（2026-09-17）

慢帧检查显示预处理、粗搜与跟踪都会增长，不支持单一热点导致全部尾延迟的判断。
本轮只优化 SmoothSampled，不改调度、搜索或精定位：

- 临时横向滤波结果不再复制输入图及 domain；下采样时只分配保留列的紧凑存储。
- 横向内部区域改为 kernel 外层、独立像素内层循环，便于向量化。
  每个像素仍按同一 kernel 顺序使用 double 累加并转回 float，不使用 fast-math。
- 纵向读取紧凑的连续列，边界仍使用原夹取规则，domain 采样规则不变。

扩展回归覆盖 10 种宽度、4 种高度、5 种 sigma：200 组平滑与 40 组下采样逐像素相等，
包含 1 像素宽、奇数尺寸、内部区域为空以及带 mask 的输入；在 1/4/无效线程设置下验证。
11 项 CTest 通过，普通 build/ 已重新构建。样例前后完整 CSV 逐字节一致，7/7 检出；
HALCON very_high 位置 RMSE 0.0779932553px，最大 0.1475394213px。

4 线程、预热 20 次、每轮 500 帧，按旧/新/旧/新顺序执行：

| 配置 | 整帧中位 / ms | P95 / ms | 预处理中位 / ms |
|---|---:|---:|---:|
| 修改前，第 1 轮 | 19.128 | 22.410 | 6.337 |
| 修改后，第 1 轮 | 18.367 | 25.321 | 5.580 |
| 修改前，第 2 轮 | 19.036 | 25.592 | 6.291 |
| 修改后，第 2 轮 | 18.494 | 21.224 | 5.800 |

两轮整帧中位数下降约 4.0% / 2.8%，预处理减少约 0.76 / 0.49ms；
其他阶段中位数相近，评估位姿数始终为 137143。
同机独立 640×480 滤波微基准（预热 20、1000 次均值）：Smooth(.8) 5.381→4.143ms，
Downsample 0.958→0.555ms。孤立函数的内存/调度环境不同，不直接换算为整帧收益。

**P95 仍波动，尚未证明尾延迟稳定改善，P95 ≤20ms 未达标。**
这次保留改动的依据是重复测得的预处理与整帧中位收益，以及逐值等价验证。
后续优先测量候选跟踪的线程负载分布，区分计算不均与系统调度等待，不预先改变候选数量。

完整数据：[filter_optimization_measurements.json](filter_optimization_measurements.json)。
复测使用 `build/performance_bench 500 /tmp/filter-benchmark.json`；训练和 I/O 不在匹配计时内。

## 第四轮：跨帧模型缓存（2026-09-17）

本轮不改变搜索网格、候选淘汰或 very_high 精定位：

- 建模时预选每层粗搜索的 12 点子集，顺序与原逐帧选择一致。
- 首次搜索按实际参数生成角度/尺度网格及变换点，后续帧复用。
  缓存属于训练数据；键包含层级、角度起止、实际尺度上下限、角度/尺度步长。
  重训练创建独立缓存，诊断工具复制训练数据时不复制缓存。
- 单个模型保留一个网格，估算数据容量上限 8MiB（不含分配器开销）；超限使用原逐变换计算。
  互斥保护构建/发布；搜索持有不可变条目的 shared_ptr，参数切换不破坏在途搜索。
  并发使用不同参数的在途条目可能暂时共存，因此不是进程总内存硬上限。
- 精定位点数不超过 1200 时直接引用模型点，避免每个候选复制；更大模型仍按原规则选择子集。
  不缓存任何场景观测、候选或匹配结果。

## 第三轮：候选内缓存与重复评分消除（2026-09-17）

未修改启发式剪枝、候选束、搜索范围或精定位迭代预算。新增：

1. `ImproveCoordinate` 返回 `{pose,best}`，调用者不再对相同最终位姿重复评分。
2. `TranslationScoreCache` 保存固定模型特征的旋转/缩放坐标与法线，仅用于 x/y 平移试探。
   平移之后仍重新取整像素、查询场景边缘和计算分数；不缓存图像观测或最终位姿结果。
3. 角度、尺度任一改变时重建；每个工作线程拥有独立缓存，在本次同层候选批次中复用分配。
   模型/层切换建立新缓存，无共享可写缓存，也不跨帧复用旧图像结果。

当前每点缓存约 40 字节，96 点约 3.75KiB/线程。未增加无界的位姿哈希表。
缓存中保留浮点相对坐标，不使用粗搜索的整数像素偏移替代亚像素平移。

## 第二轮：评分热点

继续保留搜索范围、特征点数、候选数量及精定位参数，仅做等价计算优化：

## 保留的改动

1. 默认线程上限从 32 改为 4；用户仍可通过 `SHAPE_MATCH_NUM_THREADS` 显式覆盖。
   这是针对小图、多次短任务提交的保守默认，不代表所有硬件与大图的最优配置。
2. `SmoothSampled` 合并高斯滤波与下采样：水平只计算保留列，垂直只计算保留行。
   保持 sigma、边界夹取、像素坐标映射和每个像素的双精度累加顺序。
   内部像素不再重复夹取横向索引；垂直累加按行连续访问。
3. `performance_bench` 改为预热 20 次，输出每帧预处理、粗搜、跟踪、精定位耗时、
   评估位姿数量以及 Linux RSS/线程数量。资源采集在匹配内部计时之外。
4. 新增标量参考回归：多个 sigma、窄图、奇数尺寸、mask 下的平滑与下采样逐像素一致。

未更改候选束、阈值、模板边缘点数和精定位迭代规则。
试验过候选评分提前退出，但未见稳定收益，已撤回。
本机指令集构建使用已有 `SHAPE_MATCH_NATIVE` 选项，没有将不可移植指令设为默认。

## 连续变慢的排查结论

原始 8 线程、预热 20 次后测试 100 次：中位 62.50ms、P95 67.08ms。
评估位姿数量固定 137143，线程数固定 8，RSS 从约 6.7MB 到 7.5MB；
预处理、粗搜、跟踪和精定位同时变慢。没有发现候选数量膨胀或线程不断创建的证据。
容器 CPU quota 未限制，读取的 throttled 计数为 0。
这些观测不能彻底排除内存问题，也不能单凭它们认定是 CPU 降频。

优化前的线程对照（每组预热 20 次、测量 40 次）：

## 运行

```bash
bash scripts/build.sh
./build/performance_bench 500 /tmp/shape-speed.json
./build/match_sample --output-dir /tmp/shape-speed-results
python3 scripts/compare_gt.py /tmp/shape-speed-results/matching_results.csv \
  --reference data/reference/halcon_least_squares_very_high.csv --max-rmse .078 --max-error .148
```

性能 JSON 旁会生成 `.json.csv`；前缀应使用新的临时路径以保留已有测量。
本机指令集构建可用 `cmake -S . -B build-native -DCMAKE_BUILD_TYPE=Release -DSHAPE_MATCH_NATIVE=ON`，
这种二进制不保证能在不同 CPU 上运行。
